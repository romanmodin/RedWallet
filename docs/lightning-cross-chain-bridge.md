# XBT → SHA256 Lightning bridge (in development)

Work is isolated from the pending combined Lightning candidate. No real funds may be spent during development.

The processor picker must precede any quote or disclosure of the invoice. Initially Kilombino is the only implemented provider; no placeholders are advertised as working processors. Normal XBT invoices continue through the existing native flow. BOLT12 remains separate.

Protocol evidence: Kilombino/kilobridge ab6080a4826a315217790c78908404fd4121c8d5, web/server.js and web/bolt11.js; Kilombino/lightning-fork-bridge b67e9d004cb43ef376b5b07e6dbc397effe7459e docs/payer-api.md; Kilombino/kilowallet e368766168dff16ea2302cd5ced8860dc019b3ef Bridge.kt and Lightning.kt. HTTPS public endpoint returned 403 in the development environment; linked Discord messages could not be fetched. Live service compatibility is not yet verified.

Both chains use lnbc. Signed feature 512 or 513 identifies XBT; the hold invoice must carry that feature, the original SHA256 payment hash, the pinned bridge destination, a bounded CLTV and the exact quoted millisatoshi amount. pay_sat is rounded UP by the public API, not necessarily an integer-satoshi hold invoice. rate is outgoing SHA256 per incoming XBT; spread is added before rounding.

The public status endpoint uses the ORIGINAL payment hash (also the hold hash), hex; token reveals a hex preimage. settled on the website alone is not success. A local XBT LND terminal payment with a matching SHA256 preimage must establish settlement. Failed/expired bridge status cannot release an uncertain local payment. Quote expiry is not an HTLC refund deadline.

Implemented: provider picker before disclosure; quote review/countdown/explicit authenticated confirmation; per-node Keychain journal with a durable submitting boundary; restart/status reconciliation without retries; native exact-msat XBT payment and SHA256 preimage verification; graph-only routing estimate (no payment probe); wallet history annotation and protected receipt view. The current backend is the existing embedded iPhone XBT LND. The backend interface permits another adapter, but an Umbrel remote adapter and Android native adapter are not implemented here. Other processors are not advertised as available.

Initial validation: 24 protocol/state tests plus four processor-picker component tests; existing Lightning screen, home and privacy regression suites (120 tests total) pass. Six native Swift validation/proof tests are added and pending execution. Full TypeScript passes. Gitar approved the initial provider foundation; full implementation review and native build remain pending. No real-network payment has occurred. No build or TestFlight readiness is claimed.

Local safety review: no private keys, seeds or macaroons enter the HTTP provider; only selected-processor invoice/PoW/status requests. Normal HTTPS verification stays enabled. The quote is revalidated centrally even if a future provider adapter returns unchecked data. Storage or node-history failures fail closed. Missing payment history after the durable submission boundary never permits retry. Bridge terminal state alone cannot mark success or release a local attempt. Local successful state requires a matching preimage, exact payment amount and fees within the reviewed ceiling.

Limitations: source-level protocol verification is not live service compatibility. A small real-network test needs separate explicit authorization. No automatic background execution beyond the separately implemented iOS grace period is promised. Unresolved records are never automatically deleted or reset. History has a 200-record cap and fails closed rather than evicting duplicate-payment guards. Refund timing is governed by Lightning HTLC resolution, not quote expiry. Routing estimates are graph lower bounds; the approved fee ceiling is the enforceable maximum.
