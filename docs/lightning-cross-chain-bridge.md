# XBT → SHA256 Lightning bridge (in development)

Work is isolated from the pending combined Lightning candidate. No real funds may be spent during development.

The processor picker must precede any quote or disclosure of the invoice. Initially Kilombino is the only implemented provider; no placeholders are advertised as working processors. Normal XBT invoices continue through the existing native flow. BOLT12 remains separate.

Protocol evidence: Kilombino/kilobridge ab6080a4826a315217790c78908404fd4121c8d5, web/server.js and web/bolt11.js; Kilombino/lightning-fork-bridge b67e9d004cb43ef376b5b07e6dbc397effe7459e docs/payer-api.md; Kilombino/kilowallet e368766168dff16ea2302cd5ced8860dc019b3ef Bridge.kt and Lightning.kt. Initial Python-default requests returned 403. Subsequent normal HTTPS GET /api/info and /api/pow with User-Agent RedWallet returned 200 and matched the inspected schema (including direction availability and supplied PoW difficulty). The mobile client uses that application identifier. Linked Discord messages could not be fetched. No live quote/payment or end-to-end service compatibility is claimed.

Both chains use lnbc. Signed feature 512 or 513 identifies XBT; the hold invoice must carry that feature, the original SHA256 payment hash, the pinned bridge destination, a bounded CLTV and the exact quoted millisatoshi amount. pay_sat is rounded UP by the public API, not necessarily an integer-satoshi hold invoice. rate is outgoing SHA256 per incoming XBT; spread is added before rounding.

The public status endpoint uses the ORIGINAL payment hash (also the hold hash), hex; token reveals a hex preimage. settled on the website alone is not success. A local XBT LND terminal payment with a matching SHA256 preimage must establish settlement. Failed/expired bridge status cannot release an uncertain local payment. Quote expiry is not an HTLC refund deadline.

Implemented: provider picker before disclosure; quote review/countdown/explicit authenticated confirmation; per-node Keychain journal with a durable submitting boundary; restart/status reconciliation without retries; native exact-msat XBT payment and SHA256 preimage verification; graph-only routing estimate (no payment probe); wallet history annotation and protected receipt view. If the screen loses focus or the app leaves the foreground during the app-side preflight after authentication, the approval is invalidated. The native preflight also invalidates the approval if iOS leaves the foreground before the payment RPC starts. After the RPC starts, an interruption leaves the payment tracked for reconciliation. The current backend is the existing embedded iPhone XBT LND. The backend interface permits another adapter, but an Umbrel remote adapter and Android native adapter are not implemented here. Other processors are not advertised as available.

Validation: tests cover the protocol, processor selection and cancellation, durable submission and restart recovery, and HTTPS isolation. The baseline bridge build at `6d309fb01e5775daf622116f350d16e9bc1f1e64` compiled for iOS and all twelve bridge Swift tests passed in its [wallet and payment simulator jobs](https://github.com/romanmodin/RedWallet/actions/runs/43840158813), including redirect refusal, cancellation and local settlement proof. That run's separate Tor recovery check did not pass: the first fee read after restart returned HTTP 503. The approval-lifetime change adds local regressions for leaving and returning to the app and interruption during secure storage, plus a Swift lifecycle regression. Each new source commit must repeat the native and release checks. No real bridge payment or TestFlight readiness is claimed.

Local safety review: no private keys, seeds or macaroons enter the HTTP provider; only selected-processor invoice/PoW/status requests. Normal HTTPS verification stays enabled. The quote is revalidated centrally even if a future provider adapter returns unchecked data. Storage or node-history failures fail closed. Missing payment history after the durable submission boundary never permits retry. Bridge terminal state alone cannot mark success or release a local attempt. Local successful state requires a matching preimage, exact payment amount and fees within the reviewed ceiling.

Limitations: source-level protocol verification is not live service compatibility. A small real-network test needs separate explicit authorization. No automatic background execution beyond the separately implemented iOS grace period is promised. Unresolved records are never automatically deleted or reset. History has a 200-record cap and fails closed rather than evicting duplicate-payment guards. Refund timing is governed by Lightning HTLC resolution, not quote expiry. Routing estimates are graph lower bounds; the approved fee ceiling is the enforceable maximum.
