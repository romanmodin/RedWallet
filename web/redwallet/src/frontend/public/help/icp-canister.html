Set up your own ICP canister

A detailed guide for the Advanced HTTPS adapter option. Your existing wallet stays open in its original tab.

1. First, choose the right connection

On ICP, the word is canister: an application running on the Internet Computer. A Docker container is a program running on your own computer. This setup uses both: a local bridge container and an ICP adapter canister.

Option in SettingsWhat you provideYour own canister?
Built-in RedWallet serviceNothing. The shared service is ready to use.No
My home FulcrumOne working wss:// WebSocket URL.No
Advanced HTTPS adapterYour bridge HTTPS URL, its configured Fulcrum host/port/TLS, and your adapter canister ID.Yes

For the easiest private wallet connection, use direct WSS. Wallet lookups and signed transactions go directly from your browser to your own Fulcrum. The hosted app and Auto price service still use public infrastructure.

Continue below if you want the HTTPS adapter architecture we use. The adapter makes authenticated HTTPS requests to your bridge; the bridge talks to your Fulcrum over TCP/TLS. Neither service receives your recovery phrase or private keys.

Our shared adapter is configured for our node. Entering someone else's Fulcrum address cannot reconfigure it. Your own adapter is a separate deployment.

2. Gather the prerequisites

  • A synchronized XBT / BLAKE2b-compatible node and Fulcrum. An ordinary Bitcoin-only server will fail RedWallet's checkpoint check.
  • A Linux host with Docker Compose, Git, and Node.js for the private operator tools. These commands assume Linux host networking; Windows and macOS need adapted networking.
  • A public HTTPS hostname with a trusted certificate, forwarding to your bridge. ICP must reach it from the public internet; a LAN-only address or private VPN hostname is insufficient.
  • A separate Caffeine project/account with publishing access and credits, or a developer-managed ICP deployment preserving this backend's migration chain.
  • A private directory outside your source checkout for the bridge secret and operator identity. Keep a secure backup of the operator identity.

An endpoint is the address at which a service answers requests. Example bridge endpoint: https://bridge.example.com. A canister ID identifies your deployed ICP backend; it is neither your Fulcrum hostname nor your Caffeine project ID.

Use the reviewed source on the RedWallet web deployment branch. Its deploy/adapter/README.md and deploy/umbrel/README.md are the operator references. This is an advanced installation, not a one-click canister installer.

git clone --branch web/caffeine-bridge-deployment \
  https://github.com/romanmodin/RedWallet.git redwallet-source
cd redwallet-source/web/redwallet

3. Run your own bridge container

  1. Create a private installation directory, for example ~/redwallet-bridge. Copy the repository's deploy/umbrel/compose.yaml there and place the source checkout at ~/redwallet-bridge/repository, as its build path expects.
  2. Create a private .env in the installation directory. Restrict the directory to your account and the file to mode 600. Generate a random secret locally, for example with openssl rand -hex 32, and save it as BRIDGE_SECRET. Do not put it in a prompt, source archive, browser field, or Git commit.
  3. Add the checkpoint values below. Retrieve and independently verify the exact extended header for block 961640 against your XBT node. Copy that verified header into CHECKPOINT_HEADER_HEX; the placeholder is not a working value.
# Private .env — replace placeholders before starting
BRIDGE_SECRET=YOUR_LOCALLY_GENERATED_RANDOM_SECRET
CHECKPOINT_HEIGHT=961640
CHECKPOINT_HASH=0000000000000050c1e5f69672f459293be14f46e5a494e7a8c8541396f18eeb
CHECKPOINT_HEADER_HEX=YOUR_INDEPENDENTLY_VERIFIED_EXTENDED_XBT_HEADER
ENABLE_BROADCAST=false

The supplied Compose file sets the bridge listener to 127.0.0.1:8090 and Fulcrum to 127.0.0.1:55001 with TLS off. Those example ports match our Umbrel. Edit Compose's environment values for your installation; they override matching .env entries. Loopback means “this host as seen by the bridge,” not the user's phone.

Plain Fulcrum TCP is accepted only at literal loopback. If Fulcrum is on another machine, use its verified TLS port and set FULCRUM_TLS: "true". Keep the bridge HTTP listener on loopback behind your HTTPS reverse proxy.

cd ~/redwallet-bridge
chmod 700 .
chmod 600 .env
docker compose --project-directory . -f compose.yaml up -d --build
docker compose --project-directory . -f compose.yaml ps
curl -i http://127.0.0.1:8090/health

Configure your reverse proxy/tunnel so https://bridge.example.com forwards to http://127.0.0.1:8090. The root base URL is what you enter in RedWallet; do not append /rpc. Test /health publicly. An unauthenticated request to /rpc must be rejected with 401.

Health alone does not prove Fulcrum or ICP connectivity. Keep request limits, quotas, certificate validation and the checkpoint gate enabled. Read-only setup comes first. Sending through this adapter requires your explicit later ENABLE_BROADCAST=true choice and a container restart; only already signed transactions are accepted.

4. Deploy a separate adapter canister

Create your private operator identity

Use the repository's @icp-sdk/core dependency in a private operator directory. This example creates an Ed25519 identity locally and prints only its public principal. Install Node dependencies in that directory first:

cd ~/redwallet-bridge
mkdir -m 700 operator
cd operator
npm init -y
npm install @icp-sdk/core@5.3.0
node --input-type=module <<'JS'
import fs from 'node:fs';
import { Ed25519KeyIdentity } from '@icp-sdk/core/identity';
const identity = Ed25519KeyIdentity.generate();
fs.writeFileSync('operator-identity.json',
  JSON.stringify(identity.toJSON()), { mode: 0o600, flag: 'wx' });
console.log(identity.getPrincipal().toText());
JS

Keep operator-identity.json private. The public principal can appear in your backend source. The private identity file cannot.

Route A — Caffeine project

  1. Make a new, independent project in your own Caffeine account. Do not import your changes into the shared RedWallet project.
  2. Prepare a source archive from web/redwallet, keeping its dependencies and complete enhanced-migration chain. Exclude private files, .env, operator identities, local build caches and node_modules.
  3. For this fresh installation only, replace the public operator principal in src/backend/migrations/20260929_083000.mo with the principal you just generated. Retain the controller-only setter and disabled first-user admin promotion. Do not rewrite an already deployed migration to rotate operators.
  4. Use the project's Import code action with that prepared archive. Review the compiled draft and export its source to check the import. Preserve the private-operator authority and the existing checkpoint rules; a generic new canister does not implement RedWallet's adapter API.
  5. Publish the new project. Record its live backend canister ID, not its frontend ID or temporary draft ID. If the platform does not expose it clearly, ask it to identify the live backend canister and inspect its deployment configuration.
  6. Verify that the operator-signed getBridgeOperatorStatus reports isOperator=true before configuring secrets. If the fresh migration did not appoint your identity, have the canister controller call setBridgeOperator(yourPublicPrincipal). Signing into the app does not grant controller authority.

Caffeine creates and hosts the deployed canisters. Its controller access is platform-managed; do not assume your ordinary login gives you a local controller key. Establish a supported controller/recovery procedure before relying on your deployment.

Route B — developer-managed ICP

Use your own deployment identity and ICP toolchain to build and install the backend with its full migration workflow. This repository uses caffeine.toml and enhanced migrations; a generic dfx deploy command without compatible configuration is not a complete installer. A developer must prepare that configuration and verify initialization, API and upgrades.

Once deployed, the controller appoints your public operator principal using setBridgeOperator. For developer-managed canisters, keep controller recovery access and fund/monitor cycles yourself. See the official ICP deployment lifecycle and cycles management guide.

5. Configure, verify, then connect RedWallet

Copy configure-canister.mjs and verify-canister.mjs from the source's deploy/umbrel directory into your private operator directory. The configure helper reads operator-identity.json and ../.env locally, then makes an authenticated setBridgeConfig call. The secret is never entered in wallet Settings.

cd ~/redwallet-bridge/operator
node configure-canister.mjs YOUR_LIVE_BACKEND_CANISTER_ID \
  https://bridge.example.com
node verify-canister.mjs YOUR_LIVE_BACKEND_CANISTER_ID

Replace both example values with yours. The read-only verifier checks the pinned XBT checkpoint and actual status, a published test address's balance/history, and fees through your canister. Do not treat a syntax check or local container health as a successful canister test.

  1. Return to RedWallet → Settings → Network → Advanced HTTPS adapter.
  2. Click Configure existing adapter. Enter the exact Fulcrum host, port and TLS setting that your bridge actually uses.
  3. Enter your public bridge HTTPS base URL and your live backend canister ID. Our ID connects to our bridge, not yours.
  4. Decide whether to enable the optional built-in fallback. Leave it off if wallet requests must remain on your own service.
  5. Click Test connection. It must verify your entered identity and pinned checkpoint. Then click Save and confirm the active service shows yours. Reload once and check again.

Saved settings are per browser/device. Test failure does not switch your wallet to the draft connection. Changing providers preserves saved wallets and receipts but cancels payment reviews and requires fresh network checks.

6. Keep the bridge and canister running

Your local bridge needs its host, internet connection, node and Fulcrum online. Your ICP canister separately needs cycles, the fuel for computation, storage and HTTPS calls. An online canister cannot make an offline home node answer.

For Caffeine hosting, cycle monitoring and top-ups are managed automatically and charged against your Caffeine credits. Check your account's credit usage and billing options. Automatic cycle top-up and automatic credit purchases are different settings. Credits are not perpetual; frequent wallet scans and HTTP requests increase usage. See Caffeine's cycle explanation.

For a developer-managed deployment, monitor the actual canister balance with your controller identity and arrange top-ups. The official ICP guide describes balance checks and funding. Keep enough reserve for your measured workload; no fixed number of credits guarantees a lifetime.

Back up source, public deployment IDs, private operator identity and bridge configuration securely. Upgrade code with the existing migration chain. Re-test checkpoint, identity, reads and authorization after changes. Do not remove controllers or reinstall live state as a routine fix.

7. Troubleshooting

Unauthorized operator
Your identity does not match the appointed operator. A controller must appoint it; wallet login is insufficient. Do not weaken authorization.
Canister not configured
Check the live backend ID, appointed identity and successful private configuration call.
Endpoint unreachable
Check the public certificate, reverse proxy, tunnel, bridge health and node sync. ICP cannot access a private LAN address directly.
Fulcrum identity mismatch
Enter the host/port/TLS as seen by the bridge. Compose environment values override .env entries.
Checkpoint mismatch or stale tip
Check that your node is XBT-compatible and synchronized. Independently compare block 961640 and its extended header. Do not bypass the pin.
Reads work, send unavailable
The HTTPS bridge defaults to read-only. Enabling signed relay requires the operator's explicit broadcast opt-in. Never supply a private key to a server.
Low cycles or paid-call quota
Inspect balance/credit usage and wait for the quota window where applicable. Repeated retries can make usage worse.
